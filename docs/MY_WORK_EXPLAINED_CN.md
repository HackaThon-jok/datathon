# 你需要理解和亲自验证的部分

你负责把旧报表变成能重复运行的新模型，并证明结果没变。AI 起草了实现；你的责任是理解、检查和向队友解释规则。不要把尚未做过的审核或云端运行说成自己已经完成。

## 从一个例子看流程

旧 Excel 把标题、门店合计、商品明细、折扣运费、总计都放在同一张表。程序先把每个格子原样读入 RAW，再识别哪些行属于明细，把月份和门店补到每条明细，形成 STAGING。DuckDB 用 GROUP BY 和 SUM 生成 MART。

第一张表中的 89312.44 出现两次作为汇总值，明细合计又是 89312.44。把所有数字相加会得到三倍。程序只汇总中间的 362 行，保留两条汇总用于核对。

## 四个函数

打开 `analytics/pipeline.py`，按这个顺序读：

1. `extract_workbook`：Excel 转 CSV，不改业务值，加来源行号。
2. `transform`：按来源行顺序识别报表；去掉相同副本；检查坏值；把明细变成有类型的字段。
3. `reference_totals`：直接读旧 Excel 的 Total 和门店汇总作为答案。这和“把新程序再跑一次当答案”不同。
4. `run`：用 SQL 汇总、做对比、导出文件；通过才更新本地发布指针。

`analytics/athena.py` 生成云端建表、聚合、对账和发布 SQL。它本身没有执行 AWS 操作。

## 你可以向评委解释的三个选择

**为什么没有把缺失值填成 0？** 缺失表示不知道，0 表示确定没有。直接填 0 会让错误看起来正常。这里保留 NULL、记录异常、阻止发布。

**为什么去重不用 ingest_row_id？** 这个 ID 每导入一条记录都会变化。相同来源行可能被重复导入，必须结合来源文件与 source_row_id 判断。不同来源行即使 SKU 一样也不能删除。

**为什么金额一致还要失败？** 脏数据主要损坏订单数和数量。它们是同一迁移契约的一部分，金额对上不能证明全部字段正确。

## 三分钟亲手练习

1. 按 `ANALYTICS_HANDOFF_CN.md` 跑测试和 demo。
2. 打开 `docs/evidence/clean-validation.json`，找到 542、2395、89312.44，再在原 Excel 门店和 Total 行核对。
3. 打开 `dirty-validation.json`，找到 528 和 2346，说明 SUM 会忽略 NULL，所以还要检查必填值。
4. 查看 published.json，确认它仍指向 clean run。
5. 用自己的话解释为什么 `region` 是空值。确认后，在 AI_CONVERSION_LOG 中填写真实审核结果，不要照抄虚构签名。

## 约一分钟的讲解草稿

“我的部分是把旧销售报表转换成结构化模型，并验证迁移前后的一致性。旧表混合了明细和汇总，如果直接加总会重复计算。我把报表整理成带月份、门店和来源行号的明细，再生成月度门店汇总。我们用原报表已有的汇总作为独立对照。干净样本的金额、订单数和数量都一致；脏样本即使金额相同，也因订单数和数量异常而阻止发布。AI 帮助起草转换和测试，我们保留生成记录，并通过实际运行、原表核对和人工审核确认规则。”

最后一句只有在你真正做完人工检查后才能照此陈述。地区映射未提供、云端未验证时，要如实说明。
